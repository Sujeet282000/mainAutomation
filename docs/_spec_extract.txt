1. Executive Summary
This document is a complete, page-by-page build reference for a Zapier-class automation platform. It is written to satisfy two goals at once: first, to serve as an exhaustive feature catalog of everything Zapier itself offers today — every product, every step type, every settings screen, every admin control — so nothing is skipped; and second, to translate that catalog into a production specification you can hand to a team (or use solo) to build your own full-fledged automation application, including the exact third-party accounts and platforms you must create by hand before a single line of code runs.
Zapier has evolved from a simple "if this app does X, do Y in that app" connector into what it now calls an AI Orchestration Platform. The core primitive is still the Zap — a trigger followed by one or more actions — but it now sits inside a family of seven interlocking products: Zaps, Tables, Interfaces, Canvas, Chatbots, Agents, and Copilot, all connected to an integration catalog of 8,000–9,000+ apps and exposed to external AI assistants through a Model Context Protocol (MCP) server. This document covers all of it.
1.1 What This Document Contains
Complete feature catalog — every Zapier product and sub-feature, organized the way Zapier itself organizes its UI, with what each screen does and every configuration option on it.
Step-by-step UI flow — a screen-by-screen walkthrough of building a Zap, a Table, an Interface, a Canvas, a Chatbot, and an Agent, in the order a new user actually clicks through them.
Full integration map — every major app category Zapier supports, with representative apps in each, and how connections/authentication work per category.
Build blueprint — the system architecture, data model, execution engine, Piece SDK, and API surface needed to build an equivalent platform from scratch.
Manual setup checklist — the exact external accounts, platforms, API keys, and legal/compliance registrations a builder must create by hand — nothing skipped.
Roadmap and glossary — a phased delivery plan and a full glossary of every term used across the document.
1.2 How To Use This Document
Sections 2–6 are the feature and UX reference — read these to understand exactly what a Zapier-class product must do and look like, feature by feature and page by page. Sections 6–11 are the engineering specification — read these to understand how to build it, including performance targets and deployment options in sections 12–13. Sections 16–17 are the operational checklist — read these before you write any code, because most of the "cannot be automated" work (creating developer accounts, registering OAuth apps, provisioning infrastructure) has to happen first and manually.

2.5 Business Model Snapshot
Zapier bills primarily by tasks (one task = one completed action step in a Zap run). Filters, Formatter steps, and Paths branching do not themselves consume tasks. Plans run Free (100 tasks/month, 2-step Zaps only) → Professional (multi-step Zaps, premium apps, webhooks, unlimited Zaps) → Team (shared workspaces, SAML SSO, shared app connections, Premier support) → Enterprise (custom task pools, advanced governance, audit, and negotiated SLAs). Tables, Interfaces, Chatbots, and Agents historically shipped as separate metered add-on products layered on top of core plans, with basic tiers bundled into paid plans and advanced tiers priced and metered independently.
3. Complete Zapier Feature Catalog
This section enumerates every feature area of Zapier in the same grouping a builder would encounter clicking through the product, from the core Zap engine outward to Tables, Interfaces, Canvas, Chatbots, Agents, the developer platform, and admin/governance controls. Each entry lists what the feature does, every configuration option it exposes, and how it behaves at runtime — sufficient detail to write user stories and acceptance criteria against.
3.1 Zaps — The Core Workflow Engine
A Zap is a single automated workflow: one Trigger followed by one or more Actions, executed in order every time the trigger fires. Zaps are the atomic unit of the entire platform; every other product (Tables, Interfaces, Chatbots, Agents) ultimately reads from or writes to Zaps.
Zap states — Draft (editing, not live), Published/On (live and listening), Off (paused, keeps history and configuration).
Ownership & sharing — personal Zaps, team/folder-shared Zaps, and Zaps owned by a shared app connection.
Naming & organization — custom Zap titles, folders, tags/labels, and a searchable "My Zaps" dashboard with filters by status, app, and owner.
Run modes — real-time (instant, webhook-driven), scheduled/polling (checks every 1–15 minutes depending on plan), and manually triggered test runs.
3.2 Triggers, Actions & Searches
Every app integration ("app" in Zapier's directory) exposes some combination of three primitive operation types that Zaps are built from:
Trigger — the event that starts a Zap (e.g., "New Row in Google Sheets", "New Email Matching Search in Gmail"). Triggers are either instant (webhook push from the app) or polling (Zapier checks the app's API on an interval).
Action — an operation performed in an app once the Zap runs (e.g., "Send Channel Message in Slack", "Create Record in Airtable").
Search — a lookup that finds existing data in an app (e.g., "Find Contact" in a CRM) so the result can be used later in the Zap; often paired with a "Search or Create" fallback that creates the record if not found.
Action groups — some steps combine a search and a create/update into one configurable step ("Search & Create") to avoid needing two separate steps.
3.3 Zap Editor — Screen-by-Screen
The Zap editor is a vertical, top-to-bottom canvas: Trigger at the top, then each subsequent Action or logic step stacked below it, connected by a visual line. Screens/panels a builder moves through:
App & Event Selection — search or browse the app directory, then pick the specific trigger/action event for that app (each app can expose dozens of events).
Account/Connection Selection — choose an existing authenticated connection or add a new one (OAuth popup, API key field, or username/password depending on the app).
Set Up Trigger/Action — a form of input fields specific to that event; fields can be static text, dropdowns populated live from the connected account, or dynamic fields that appear based on earlier answers.
Data to Insert / Field Mapping — a right-hand or inline picker exposing every output field from all upstream steps, with expandable nested-JSON drill-down (caret icons) for deeply nested API responses, so any field can be dropped into any downstream input by click or drag.
Test Step — pulls a real, live sample record from the connected account (or lets the user pick from recent items) and shows exactly what data will flow through; required before a step can be turned on for most triggers.
Continue/Publish — once every step tests successfully, the Zap can be turned on, which registers the underlying webhook subscription, polling schedule, or event listener with the external app.
Autosave & draft state — every keystroke is saved to a draft version; nothing goes live until the Zap is explicitly turned on.
Undo/redo — full edit history within a session.
Zoom & minimap — for long, many-step Zaps.
Rename, duplicate, and move steps — steps can be reordered by drag, duplicated, or deleted without losing downstream mappings where possible.
Inline error banners — a step with missing required fields or a failed test is flagged directly on the canvas before publish.
3.4 Multi-Step Zaps
Paid plans allow unlimited additional Action steps after the first, letting a single trigger fan out into many sequential actions — e.g., a new deal in a CRM can simultaneously post to Slack, create a project in a PM tool, add a row to a spreadsheet, and send a welcome email, all inside one Zap.
Each additional step is added with a "+" control directly on the canvas at the point it should execute.
Steps execute strictly in the order shown top-to-bottom unless routed through Paths.
Any step's output fields remain available to every step below it, not just the immediately preceding one.
3.5 Paths — Conditional Branching
Paths let one trigger split into multiple mutually exclusive branches based on conditions evaluated against the trigger or any upstream step's data — Zapier's equivalent of if/then/else logic.
Rule builder — each Path has one or more condition rows (field / operator / value), combined with AND or ALL/ANY logic.
Multiple paths — A, B, C… each with its own independent rule set and its own chain of subsequent action steps.
Fallback / else path — an optional default branch that runs when no other path's conditions match.
Continue-on-no-match toggle — controls whether the Zap run is marked as "filtered out" or continues silently if nothing matches.
Path-level testing — each path can be tested independently with sample data to confirm the right branch fires.
3.6 Filters
A Filter step stops a Zap from continuing unless incoming data meets specified conditions — a single-branch gatekeeper, as opposed to Paths' multi-branch router.
Field / condition / value rows, combinable with AND/OR logic across multiple conditions.
Common operators: exists/doesn't exist, (does not) contain, (does not) exactly match, greater/less than, is (not) empty, is (not) in a list, matches regex (on higher plans).
Filters do not consume a task if the Zap is stopped at that step, making them a cost-free way to add precondition logic.
3.7 Formatter by Zapier
A built-in, no-extra-account-needed transformation step used to reshape data between the trigger and downstream actions. It does not consume a task.

3.8 Delay by Zapier
Pauses a Zap run for a specified duration before continuing to the next step. Does not consume a task for the delay itself (the following action step still does when it runs).
Delay For — a fixed duration (minutes, hours, days, weeks) from the moment the step is reached.
Delay Until — a specific date/time, either static or computed from a data field earlier in the Zap (e.g., "3 days before the deadline field").
Delay Queue — processes delayed items strictly in the order they entered the delay, useful for sequencing.
3.9 Sub-Zaps / Nested Zaps
Lets one Zap call another Zap as a reusable sub-routine, passing data in and (optionally) receiving data back — used to avoid duplicating the same multi-step logic across many parent Zaps.
A Sub-Zap is authored like a normal Zap but started by a special "Sub-Zap" trigger instead of an app event.
The parent Zap calls it with a "Run a Sub-Zap" action step, mapping input fields.
Useful for shared logic such as standardized error notification, data enrichment, or logging routines reused across dozens of parent Zaps.
3.10 Looping by Zapier
A dedicated built-in step that iterates over a list/array (e.g., line items on an order, rows in an uploaded CSV) and runs the subsequent action steps once per item, since the core linear Zap canvas has no native loop construct.
Loop source: a line-item field, a comma-separated text field split into items, or a fixed number of iterations.
Each loop iteration counts as its own task execution for every action inside the loop.
Commonly paired with Formatter's line-item transforms to prepare the array being looped over.
3.11 Webhooks by Zapier
Lets a Zap trigger from, or send to, any arbitrary HTTP endpoint — the escape hatch that connects Zapier to systems with no pre-built app integration.

3.12 Code by Zapier / Functions
Runs custom JavaScript or Python directly inside a Zap step for logic no built-in step can express — data transformation, custom API calls, complex conditionals, or calling out to a private library.
Input fields are mapped from upstream steps into named variables available inside the code sandbox.
Supports npm/pip-style standard libraries within the sandbox's allowed set; outbound HTTP calls (fetch/requests) are permitted for calling external APIs directly from code.
A recent platform update extended maximum runtime for code steps to around 10 minutes, enabling heavier multi-API workflows and larger data processing without splitting logic across multiple Zaps.
Rebranded/extended as "Functions" for reusable, testable, versioned code blocks callable from multiple Zaps.
3.13 Email Parser by Zapier
A standalone companion tool (separate mini-app) that converts unstructured inbound emails into structured trigger data for a Zap.
Generates a unique parser email address to forward or auto-forward mail to.
User highlights sample text in a sample email to teach the parser which fragments map to which named fields (e.g., "Order Number", "Total").
Parsed fields become available as trigger fields in a normal Zap once enough sample emails have been mailboxed.
3.14 Schedule by Zapier
A built-in trigger for time-based automation with no external app required.
Every N minutes/hours (paid plans), daily, weekly (with day-of-week selection), or monthly (with day-of-month selection).
Time zone configuration per schedule.
Used for recurring digests, reminders, batch syncs, and cleanup jobs.
3.15 Storage by Zapier
A simple built-in key-value store for persisting small pieces of data between separate Zap runs (e.g., remembering the last processed record ID, a running counter, or a dedupe list) without needing an external database or Table.
Set Value, Get Value, Increment Value action/search steps.
Scoped per Zapier account with a defined size limit per key and total keys, suitable for lightweight state, not bulk data (use Tables for that).
3.16 Digest by Zapier
Collects multiple trigger events over time and releases them together as a single batched summary instead of firing downstream actions once per event.
Digest name groups related entries together; each incoming item is appended with a template (e.g., "{{Name}} signed up on {{Date}}").
Release schedule: a specific time daily/weekly/monthly, or manually via a separate release trigger.
Downstream step receives the full compiled digest text as one field — ideal for daily summary emails or reports.
3.17 Human-in-the-Loop: Approvals & Conditional Forms
Several features let a Zap pause for a human decision rather than running fully unattended.
Zapier Interfaces Forms — collect structured input and can gate a workflow behind a submitted approval form.
Conditional logic in Forms — on paid Interfaces tiers, later questions can be shown/hidden dynamically based on answers to earlier questions.
Email/Slack "Approve or Deny" actions — many communication app integrations expose interactive buttons that write a decision back into the Zap's data for downstream branching via Paths.
Agent human-approval checkpoints — Agents can be configured to require explicit human sign-off before taking a sensitive action (e.g., sending an external email or processing a payment).
3.18 Zapier Tables
An automation-native relational database built directly into the platform, positioned to remove the need for a separate lightweight database tool for many workflows.
Structure — Bases contain Tables; Tables contain typed Fields (text, number, date, checkbox, single/multi-select, attachment, link-to-another-record, formula, AI field) and Records (rows).
Views — grid view plus filtered/sorted saved views.
Triggers — New Record, Updated Record, New or Updated Record, Deleted Record.
Actions — Create Record, Update Record, Find Record, Find or Create Record, Delete Record, Create Table, Bulk actions on paid tiers.
AI fields — a field type that runs a prompt against a connected AI model per-row to enrich or classify data automatically as records are added.
Automations tab — table-native, lightweight automation rules that can run without leaving Tables (e.g., "When Status changes to Done, send Slack message") in addition to full Zap triggers.
Access — the free tier includes unlimited tables at a base capacity; higher tiers raise record limits, add advanced permissions, and bulk operations.
3.19 Zapier Interfaces
A no-code builder for forms, web pages, and lightweight internal apps that plug directly into Zaps and Tables — used to give a workflow a human-facing front end without a separate website builder.
Components — Forms (single or multi-page, with conditional/dynamic question logic on paid tiers), Pages (static content blocks, embedded Tables views, images, buttons), and Apps (multi-page experiences combining forms, tables, and navigation into an internal tool such as a lightweight CRM or intake portal).
Form field types — short/long text, single/multi-select, dropdown, file upload, date, rating, signature, hidden fields for pre-filled context, payment collection on eligible plans.
Publishing — hosted on a Zapier subdomain, embeddable via iframe/JS snippet on an external site, or password-protected for internal-only use.
Triggers — "New Form Submission" and "New Interface Interaction" start Zaps directly from user activity on the Interface.
Theming — logo, color palette, and custom domain on higher tiers for white-labeled experiences.
3.20 Zapier Canvas
A free, AI-assisted visual diagramming tool for planning a business process before (or instead of) building it step-by-step in the Zap editor; Canvas plans can be turned directly into live Zaps, Tables, Interfaces, Agents, and Chatbots.
Nodes — process steps, decision/split-path nodes, and "default steps" that represent human/team-dependent actions not yet automated.
Automated steps — nodes that add or pull in existing Zap workflows, including Interfaces, directly onto the canvas.
Grouped nodes — clusters that organize a complex, multi-team process into readable sections.
On-canvas field mapping — map inputs/outputs between connected nodes without leaving Canvas to open the full Zap editor.
Agent support — Agents can be added and configured directly from within Canvas.
Zapier asset builder — type a description into a node and use AI to turn that text into a real Zap, Interface, Chatbot, or Table.
Time-saved & activity metadata — Canvas can display estimated time saved and live run/record/submission counts for every connected asset, turning the diagram into a live operations dashboard.
Auto-generated Canvas — the platform can automatically generate a Canvas diagram of how a company's existing Zaps, Tables, Interfaces, Chatbots, and Agents relate to one another, fully editable afterward.
Rich text & sharing — images, links, checklists, custom colors, and shareable/collaborative editing for cross-team alignment.
3.21 Zapier Chatbots
A no-code builder for AI chatbots trained on a business's own content and connected to automation, used for customer support, lead capture, and internal FAQ deflection.
Knowledge sources — uploaded documents, URLs to crawl, and connected help-center content, used to ground chatbot answers.
Custom instructions/prompt — defines tone, scope, and behavior boundaries for the bot.
Actions from chat — a chatbot conversation can trigger a Zap directly (e.g., "create a support ticket", "look up an order"), turning chat into a two-way automation surface, not just Q&A.
Deployment — embeddable widget on a website, a hosted standalone chat link, or integration into existing support channels.
Lead collection — structured capture of visitor contact details mid-conversation, feeding directly into CRM Zaps.
Org-wide admin control — administrators can disable Chatbots across an entire organization from a central control (as a governance/compliance lever).
3.22 Zapier Agents (Central)
Zapier's autonomous AI-teammate product: goal-oriented agents that reason, plan, and take multi-step actions across connected apps rather than following a single fixed trigger-action path.
Goal / instructions — defined in natural language — what the agent is responsible for and the boundaries it should respect.
Connected tools — the specific apps, actions, Tables, and Zaps the agent is permitted to use, scoped explicitly rather than given blanket access.
Reasoning models — agents can be configured against different underlying LLMs depending on task complexity and cost/quality tradeoffs.
Monitoring mode — agents can passively watch a data source (inbox, table, feed) and act only when their conditions are met, rather than waiting for a discrete external trigger.
Human oversight — approval checkpoints, activity logs, and the ability to pause/edit an agent's permissions at any time.
Agent templates — a library of ready-made agents (e.g., lead enrichment, lead scoring & routing, meeting follow-up assistant, candidate ranking, brand-voice/content checker) that can be launched and customized in minutes from the Templates hub.
Enterprise controls — audit logs, managed credentials, and admin controls consistent with the rest of the platform's governance model.
Non-determinism disclosure — Zapier explicitly documents that agents, being LLM-driven, will not always behave identically run to run, unlike deterministic Zap steps, and that agents can only act within the specific apps, triggers, and actions they have been explicitly connected to.
3.23 Zapier Copilot
An AI build-assistant embedded across every product surface (Zaps, Agents, Chatbots, Canvas, Tables, Interfaces) that turns a plain-language description into a working configuration.
Describe a desired automation in a sentence; Copilot proposes the trigger, actions, and field mappings, then lets the user review and adjust before publishing.
Can refine an agent's instructions automatically when test runs do not behave as intended.
From a single prompt, Copilot can architect a cross-product solution: a Canvas plan, a Table schema, a Forms input layer, and the connecting Zaps, together.
Supports voice input for dictating build instructions, and can construct custom API actions on the fly when no pre-built app action covers a need.
3.24 AI Actions / AI by Zapier / AI Fields
First-class AI model steps usable inside any ordinary Zap, independent of the standalone Agents product.
AI by Zapier action step — prompt-driven text generation, summarization, classification, extraction of structured data from unstructured text, translation, and sentiment/intent detection, insertable as a normal step in any Zap.
Model choice — steps can be pointed at different providers/models (e.g., GPT-4o-class, Claude, Gemini-class models) depending on the account's connected AI provider keys or Zapier's managed model access.
Vision & transcription — image-understanding prompts and audio transcription as callable step types.
AI fields in Tables — a field type that automatically enriches or classifies each record with a model call as data is created or updated.
Custom/API actions via AI — Copilot or the action-builder can generate a working custom HTTP action against an arbitrary API description without a pre-built app Piece existing yet.
3.25 Zapier MCP (Model Context Protocol)
An integration layer that exposes Zapier's entire app catalog and tens of thousands of underlying actions as callable tools to any external AI assistant that supports the MCP standard, including general-purpose chat assistants and custom agents built on other frameworks.
Lets an external AI client take real-world actions ("send this email", "create this ticket", "look up this contact") without a human first building a dedicated Zap for that exact task.
Positions Zapier as a universal action/tool layer sitting underneath many different AI front ends, not just its own products.
Access and permission scoping follow the same connected-account model as the rest of the platform — an MCP client can only call actions the underlying Zapier account is authorized for.
3.26 Transfer by Zapier
A bulk, one-time (or repeatable) data-migration tool distinct from the ongoing, event-driven behavior of a normal Zap — used to move existing historical records between two apps rather than reacting to new events.
Select a source app/object and a destination app/object, map fields once, then run the transfer across all existing matching records.
Useful for initial backfills before turning on a live Zap that only reacts going forward (e.g., migrate 5 years of existing contacts, then let a Zap handle new ones).
3.27 Zap Templates & Template Gallery
A searchable library of pre-built Zap, Agent, Table, Interface, and Chatbot configurations for common use cases, browsable by app, category, or team function.
One-click "Use this template" pre-fills the trigger/action apps and typical field mappings, leaving only account connection and final field confirmation to the user.
Agent templates specifically surface proven, goal-defined agents (lead enrichment, scoring/routing, meeting follow-up, HR candidate ranking, brand-voice checking, etc.) directly from the same Templates hub as Zap templates, so AI workflows are discoverable in one place rather than built from scratch.
Templates are also promoted contextually inside Canvas and inside individual app directory pages.

6.2 Execution Engine — Runtime Internals
An event arrives at the Trigger Service (webhook push or a polling tick discovers new data).
The Trigger Service normalizes the payload into the workflow's internal event schema and enqueues a new Run.
The Execution Engine picks up the Run and walks the workflow's step graph top-to-bottom, evaluating Filters and Paths as boolean gates against accumulated run data.
For each Action/Search step, the Engine invokes the Piece/Connector Runtime in an isolated sandbox with the mapped input fields resolved from all prior step outputs.
Each step's result (success payload or error) is persisted immediately to the Run's history record, before moving to the next step — this is what powers per-step Zap History inspection.
Transient failures are retried on an exponential backoff policy up to a configured limit before the Run is marked failed and an error notification is dispatched.
Delay and Digest steps suspend the Run (or a per-item sub-run) and re-enqueue it for resumption at the scheduled time rather than holding a worker thread idle.
A completed Run's task count is reported to the Billing & Metering Service in the same transaction as the final step result.
6.3 Multi-Tenancy & Isolation
Every Run, Connection, Table, and Interface record is scoped by tenant/workspace ID at the database layer, enforced by row-level security, not just application logic.
The Piece/Connector Runtime executes third-party and user-authored code (Code steps, custom Pieces) in a sandboxed, resource-limited container per invocation, with no shared state or filesystem across tenants.
Secrets are encrypted per-tenant with envelope encryption; a compromised worker node must not be able to decrypt another tenant's credentials.

10. AI & Agent Orchestration Layer
10.1 Model Routing

Per-workspace model preferences and BYO-API-key support let enterprise customers control cost and data-handling terms.
10.2 Agent Runtime
An Agent record defines its goal, an explicit allow-list of tools (mapped 1:1 to existing Piece actions/searches and Table operations), a trigger mode, and an approval policy.
On activation, the Agent Runtime maintains a reasoning loop: observe (new event or polled state) → plan (LLM call proposing a next tool call) → check against the allow-list and any approval policy → execute the tool call through the same Piece Runtime used by ordinary Zaps → observe the result → continue or stop.
Every planning step and tool call is written to an immutable Agent Activity Log, mirroring Run Step Results for Zaps, so agent behavior is fully auditable after the fact.
Approval-required actions pause the loop and create a pending approval item (deliverable via Interfaces, Slack, or email) until a human responds.
10.3 MCP Server Layer
Exposes the full Piece catalog as MCP-compatible tool definitions so any external MCP-aware AI client can call them directly, subject to the same per-connection authorization scope as the rest of the platform.
Each MCP tool call is logged through the same Run/audit infrastructure as an internal Agent tool call, so external-assistant activity is not a governance blind spot.

Org-wide policy toggles for which AI surfaces (Chatbots, Agents, AI Actions) are enabled at all.

12. Connections, Apps & Workflows — How They Actually Bind, Technically
This section goes underneath the no-code UI and explains, in real engineering terms, what happens when a user clicks "Connect," picks an app, and builds a flow — how a Connection object, an App/Piece definition, and a Workflow (Zap) graph are actually wired together at runtime, and how data physically moves between steps. Everything in Section 3 describes what the product does; this section describes how it is built underneath.
12.1 The Three Objects That Get Bound Together
Object
What It Really Is
Where It Lives
App / Piece Definition
A versioned code package declaring an auth scheme plus one or more trigger/action/search functions and their input/output schemas
Shipped as a package in the Piece registry; loaded by the Piece Runtime at execution time, never per-tenant
Connection
A row in the Connections table: a specific set of encrypted credentials (OAuth tokens or API keys) tied to one App Piece and one owning tenant/user
Connections table + encrypted secrets vault; referenced by ID, never embedded directly in workflow config
Workflow / Zap Graph
A directed graph of Step nodes, each pointing at an App Piece's specific trigger/action, a Connection ID to use, and a Field Mapping describing where its inputs come from
Workflow/Step tables; the graph itself holds no credentials, only references
The critical design point: a Step never stores credentials directly. It stores a connection_id foreign key. This is what lets one Connection be reused across many Zaps (and, on Team plans, across many users) without re-authenticating, and lets a credential be rotated or revoked in one place without touching every workflow that uses it.
12.2 What Actually Happens When a User Clicks "Connect"
The browser calls POST /connections/init with the chosen app_key. The API looks up that Piece's auth_schema (OAuth2, API key, Basic, or custom) from the Piece registry.
For OAuth2: the API builds an authorization URL using the Piece's declared client_id, scopes, and a redirect_uri pointing back at the platform's own OAuth callback endpoint, then opens it in a popup.
The user authenticates on the third-party app's own site (Google, Slack, Salesforce, etc.) — the platform never sees the user's third-party password, only what the OAuth flow returns.
The third-party app redirects back to the platform's callback with a short-lived authorization code.
The platform's backend (never the browser) exchanges that code, server-to-server, for an access token and refresh token, using the Piece's client_secret, which is never exposed to the frontend.
The access + refresh tokens are encrypted with the tenant's data key (envelope encryption) and written to the Connections table as a new row; the browser only ever receives a connection_id back, never the raw tokens.
For API-key-based apps, the flow is simpler: the raw key the user pastes in is sent directly to the backend over TLS, encrypted, and stored the same way — the frontend never persists it, even temporarily, in browser storage.
12.3 How a Connection Gets Bound Into a Step at Build Time
In the Zap editor, when a user picks an app + event for a Step, the frontend calls GET /pieces/{app_key}/triggers/{event_key} (or /actions/...) to fetch that event's declared input field schema.
The frontend renders that schema as a form. Any field marked dynamic (e.g., "which Slack channel") triggers a live call — GET /connections/{id}/dynamic-options?field=channel — which the backend fulfills by invoking that Piece's options() function against the live third-party API using the bound Connection's credentials, so the dropdown always reflects the real, current account state, not a cached list.
When the user saves the step, the frontend persists: step.piece = app_key, step.event = event_key, step.connection_id = the chosen Connection, and step.input_config = the field values (static text or {{step_N.field}} template references).
Nothing about the third-party app's actual API shape is stored on the Step — only the Piece's abstracted field keys. This is what lets a Piece author change the underlying vendor API in a new Piece version without every existing Zap breaking, as long as the field-key contract stays stable.
12.4 How Field Mapping Physically Resolves at Runtime
A downstream step's input like {{step_2.customer.email}} is not a live pointer — it is a path expression resolved against that specific Run's accumulated data at execution time, not against the Zap definition.
When the Execution Engine finishes Step 2, it writes Step 2's full output payload into that Run's context object, keyed by step ID (run_context['step_2'] = {...}).
Before invoking Step 3, the Engine walks Step 3's input_config, and for every templated field, does a path lookup into run_context using the stored path (step_2.customer.email), substituting the resolved value.
If a referenced path is missing (e.g., the trigger app didn't return that field this time), the Engine either substitutes an empty value or halts the Run with a mapping error, depending on whether the field was marked required in the Piece's schema.
This resolution happens fresh on every single Run — it is why editing an upstream step's output shape (e.g., a Piece version upgrade that renames a field) can silently break downstream mappings until the user re-maps them, which is exactly why Piece versioning and step-level validation exist.
12.5 How a Trigger Actually Gets "Wired Live" on Publish
Instant (webhook) triggers — on publish, the Engine calls that Piece's subscribe() function, which uses the bound Connection's credentials to call the third-party app's own API and register a webhook pointed at a unique URL like https://hooks.platform.com/t/{trigger_subscription_id}. That subscription ID is stored against the Step. On un-publish/delete, unsubscribe() is called to remove the third-party webhook — leaving it registered after deletion is a common real-world bug class to guard against.
Polling triggers — on publish, a row is written into a Scheduler table (piece, connection_id, poll_interval, cursor). A scheduler service ticks on that interval, invokes the Piece's poll() function with the stored cursor (e.g., "last seen ID" or "last seen timestamp"), and only emits new Run events for records after that cursor, then advances and persists the cursor for next time.
Webhook delivery in — when the third-party app calls the platform's hook URL, an ingress service authenticates the payload (HMAC signature verification where the app supports it), maps the URL's subscription ID back to the owning Step/Connection, and enqueues a new Run onto the Task Queue — the actual Execution Engine work happens asynchronously from the inbound HTTP request, so the webhook call itself can return 200 immediately.
12.6 Binding at Execution Time — the Full Step Invocation
The Execution Engine worker picks the next queued Step invocation off the Task Queue.
It loads the Step's piece + event + connection_id + resolved input payload (from 12.4).
It loads the Connection's encrypted credentials from the vault and decrypts them in-memory, inside the sandboxed worker process, for this invocation only — decrypted credentials are never written to disk or logs.
It loads the versioned Piece code (pinned to the exact Piece version that Step was built against) into the Piece Runtime sandbox.
It calls that Piece's perform(inputData, auth) function, passing the resolved inputs and the decrypted credentials as arguments; the Piece code itself makes the actual outbound HTTPS call to the third-party app's REST/GraphQL API.
If the third-party API returns an auth error because a token expired, the Runtime automatically attempts a token refresh using the Connection's stored refresh_token before failing the Step, transparently to the workflow.
The result (or error) is written to that Run's Step Result record, merged into run_context, and the Engine advances to the next Step, repeating from 12.4.
12.7 Multi-App Binding Inside One Workflow — Worked Example
A single Zap — "New Row in Google Sheets → Create Contact in HubSpot → Post Message in Slack" — actually binds three independent Connections into one Run:
Step 1 (Trigger) is bound to Connection A (a Google account) and its Piece's poll() function; the Scheduler invokes it on an interval using Connection A's OAuth token.
Step 2 (Action) is bound to Connection B (a HubSpot account); its input_config maps {{step_1.row.email}} and {{step_1.row.name}} into HubSpot's contact-creation schema; at runtime the Engine resolves those from Step 1's actual output before calling HubSpot's Piece code with Connection B's credentials.
Step 3 (Action) is bound to Connection C (a Slack workspace); its message template interpolates {{step_2.contact.id}} — a field that only exists because Step 2 already ran and wrote its result into the shared run_context.
All three Connections are entirely independent credential objects, owned potentially by different users if the workspace uses shared app connections, but the Run itself is a single ordered execution binding all three together through the run_context object, not through any direct connection between the apps themselves.
12.8 Why This Design Matters in Practice
Rotating or re-authenticating one Connection (e.g., a Slack token expiring) never requires touching the Zap graph itself — only the Connection row changes.
A Piece can ship a new version with a different underlying vendor API call while old Zaps keep running against the pinned older Piece version until the user explicitly upgrades.
Because credentials are decrypted only inside an ephemeral sandboxed worker process per invocation, a compromised web server never has access to live third-party tokens.
Because trigger subscriptions are tracked as first-class rows (webhook subscription IDs, polling cursors), the platform can detect and self-heal a "silently dead" trigger — e.g., a webhook the third-party app stopped delivering to — rather than a Zap failing invisibly forever.

12.2 Reliability Requirements
At-least-once delivery semantics for every queued Run, with idempotency keys on action steps to guard against duplicate side effects on retry.

12.3 Scalability Requirements
Horizontal auto-scaling of the worker pool based on queue depth, independent of the web app and API tiers.
Tenant-fair scheduling so one workspace's burst of task volume cannot starve other tenants' Runs (per-tenant concurrency caps and priority lanes).
Piece Runtime sandboxes must scale statelessly — any worker can execute any tenant's step with no session affinity required.

16. End-to-End Reference Scenario
A single worked example threading together most of the feature areas above, useful as a QA acceptance scenario and as a sales demo script.
Scenario: Automated Invoice Processing with Human Approval
Trigger — an email with a PDF invoice attachment lands in a monitored "Invoices" inbox label (Gmail/Outlook trigger, or Email Parser if the source is unstructured forwarded mail).
Extraction — an AI Action step reads the attached PDF and extracts line items, vendor, amount, and due date into structured JSON.
Validation — a Filter step confirms all required fields were extracted; if not, the run stops and an error notification alerts the AP team.
Duplicate check — a Search step looks up the vendor + invoice number in Zapier Tables to prevent double-processing.
Data write — a Formatter step normalizes currency and date formats, then a Create Record action writes the invoice into an "AP Queue" Table.
Routing — a Path step branches on amount: under a threshold auto-proceeds; over the threshold requires approval.
Human approval — for over-threshold invoices, an Interfaces-hosted approval form is sent to the CFO with Approve/Deny actions; the run pauses (Delay Until / webhook callback) until a response is received.
Posting — on approval, an action step creates the bill in QuickBooks Online and updates the Table record's status field.
Notification — a Slack message confirms posting to the requester; a Digest step batches all invoices processed that day into one end-of-day summary email.
Audit — every step's input/output is retained in Zap History, and the approval decision is recorded in the Audit Log for compliance review.
This single scenario exercises: email/app triggers, AI extraction, Filters, Search/Create against Tables, Formatter, Paths, human-in-the-loop approval via Interfaces, Delay, downstream app actions, Digest, Zap History, and the Audit Log — nearly the full feature surface of the platform in one realistic business process.
17. Integration Setup Guides by Category
Practical, per-category connection setup steps — what an end user (or a builder configuring their own Piece) actually has to do to get each class of app authenticated and usable inside a Zap. Grouped by category since the steps are consistent within a category regardless of which specific app is chosen.
17.1 Google Workspace (Sheets, Gmail, Drive, Calendar)
Click Connect on the Google-based app; a Google OAuth consent popup opens.
Sign in with the Google account that owns the data to connect.
Review and accept the requested scopes (e.g., read/write access to Sheets, send-as access to Gmail) — only the scopes the specific trigger/action needs are requested, not blanket account access.
Google returns an authorization code exchanged for an access + refresh token, stored encrypted in the connection vault.
For apps requesting sensitive scopes (e.g., full Gmail access) at high user volume, the platform operator must have already passed Google's OAuth app verification review — an end user cannot work around this.
The connection is now reusable across every Zap using that Google account, without repeating the OAuth flow.
17.2 Slack
Click Connect on a Slack trigger/action; a workspace-selection screen appears.
An admin (or a user with sufficient workspace permission) approves the requested bot/user scopes (e.g., post messages, read channel list).
Slack issues a bot token scoped to that specific workspace; the connection is reusable for all Zaps targeting that workspace.
Channel/user pickers in later step configuration are populated live from the connected workspace via the Slack Web API.
17.3 CRM Platforms (Salesforce, HubSpot, Pipedrive)
Choose the specific CRM app and initiate Connect; most use OAuth, though some legacy integrations still accept an API key generated from the CRM's own settings panel.
For Salesforce specifically, the connecting user's profile must have API access enabled by their Salesforce admin, and a Connected App may need to be pre-approved in the target Salesforce org.
Once connected, custom fields and picklists defined in the CRM automatically populate as selectable options in the Zap editor's field-mapping panel — no separate configuration step is needed for standard custom-field support.
17.4 Payments (Stripe, PayPal, Square)
Connect via OAuth (Stripe Connect / PayPal) or a restricted API key generated in the provider's dashboard, scoped to read-only or read-write as needed.
Because payment data is sensitive, these connections should be flagged for additional audit-log detail and, on regulated workspaces, additional approval gating before a Zap using them can be published.
Test-mode vs. live-mode keys should be kept as separate connections so a Zap can be fully tested against sandbox data before being pointed at real transactions.
17.5 E-commerce (Shopify, WooCommerce, BigCommerce)
Shopify: install the platform's public app (or a custom app for a single store) from the Shopify admin's App section; this generates the OAuth credentials automatically.
WooCommerce/self-hosted platforms: generate a REST API key/secret pair from the store's own admin settings, since there is no central app-store OAuth flow for a self-hosted WordPress install.
Product, order, and customer fields become available as trigger/action data immediately after connection; custom fields/metafields may require an additional "fetch schema" step.
17.6 Databases (Postgres, MySQL, Snowflake)
Connections require direct network reachability: either the database must accept inbound connections from the platform's worker IP ranges (allow-listed), or a secure tunnel/VPN peering must be established.
Credentials are a database username/password or a cloud-native IAM role, entered directly rather than via OAuth.
Because direct database actions can run arbitrary queries, these connections should default to read-only credentials unless a write action is explicitly required, and every query executed should be logged for audit.
17.7 AI Model Providers (OpenAI, Anthropic, Google AI)
Generate an API key from the provider's console (platform.openai.com, console.anthropic.com, or Google AI Studio/Vertex).
Attach billing to that provider account, since these are metered pay-per-token services independent of the automation platform's own billing.
Paste the key into the connection screen, or — for platform-managed model access — simply select the model; no separate key is needed if the platform is fronting the provider relationship itself.
Set per-workspace spend ceilings where supported, since AI steps can otherwise consume budget unpredictably compared to fixed-cost app actions.
17.8 Custom APIs via Webhooks / HTTP
No pre-built Piece is required — choose the Webhooks app directly.
For an outbound action: supply the target URL, HTTP method, headers (including any auth header such as Bearer token or API key), and body template with mapped fields.
For an inbound trigger: Zapier/your platform generates a unique Catch Hook URL; that URL is pasted into the external system's own webhook-configuration screen (a manual step performed outside the automation platform, inside the third-party system).
Test with a real request before publishing, since malformed headers or an incorrect content-type are the most common first-connection failure.

18.2 Full Connect-and-Configure Walkthroughs — Top 15 Apps
For each app below: how the connection is authenticated, and the exact no-code steps to set it up as a trigger or action inside the Zap builder.
1. Gmail
In the Zap editor, search "Gmail" and choose it as the Trigger app; pick event "New Email Matching Search" (most common) or "New Attachment."
Click Sign in to Google; a Google OAuth popup opens — choose the account and approve the requested Gmail scope (read, or read+send if used as an action).
Configure the Search String field (e.g., from:billing@vendor.com has:attachment) to scope exactly which emails should trigger the Zap.
Test trigger — Zapier pulls the most recent matching email so you can confirm subject, body, sender, and attachment fields are present.
As an Action instead: choose event "Send Email," map To/Subject/Body fields from upstream steps, and test — this actually sends a real email to confirm formatting.
2. Google Sheets
Choose Google Sheets as Trigger; event "New Spreadsheet Row" (fires once per new row) is the most common choice.
Connect the Google account (same OAuth popup flow as Gmail, scoped to Sheets).
Select the specific Spreadsheet, then the Worksheet (tab) to watch — both dropdowns populate live from the connected account.
Test trigger to confirm each column maps to a named field (Column A, Column B, etc., or header-row names if the sheet uses them).
As an Action: choose "Create Spreadsheet Row," pick the same spreadsheet/worksheet, and map each column's value from upstream step data.
3. Slack
Add Slack as an Action step (most common use); choose event "Send Channel Message."
Connect Slack — a workspace picker appears; an admin approves the bot's requested scopes (chat:write, channels:read, etc.).
Pick the target Channel from a live dropdown populated from the connected workspace.
Write the Message Text, inserting mapped fields from upstream steps (e.g., "New deal: {{step_1.deal_name}} — ${{step_1.amount}}").
Optionally configure Bot Name/Icon overrides and test — this posts a real message to confirm formatting before publishing.
4. Salesforce
Choose Salesforce as Trigger; event "New Record" or "Updated Record," then pick the Object (Lead, Contact, Opportunity, or a custom object).
Connect via OAuth — sign in to the Salesforce org; the connecting user's profile must have API Enabled permission, granted by a Salesforce admin beforehand.

5. HubSpot
Choose HubSpot as Trigger or Action; common pattern: Trigger "New Deal" or Action "Create or Update Contact."
Connect via OAuth — sign in to the HubSpot account and approve the requested scopes for CRM objects.

Test the action — this creates/updates a real test contact, so use a test email address first.
6. Stripe
Choose Stripe as Trigger; event "New Charge" or "New Customer" are the most common.

As an Action: "Update Order" or "Create Customer" — map fields accordingly.

Test trigger to confirm every Airtable field (including linked records and attachments) appears as mappable data.

9. Trello
Choose Trello as Trigger; event "New Card" or "Card Moved to List."
Connect via OAuth — sign in to Trello and authorize access.

10. Mailchimp
Choose Mailchimp as Trigger; event "New Subscriber" (common for lead-capture-to-email-list flows) or as an Action "Add/Update Subscriber."

11. Zoom
Choose Zoom as Trigger; event "New Meeting Registrant" or "Recording Completed" are common.

22. Testing & QA Strategy
23.1 Test Layers
Unit tests — every Piece's trigger/action/search functions, tested against recorded API fixtures.
Contract tests — verify a Piece's declared input/output schema matches what the live third-party API actually returns, run on a schedule to catch upstream API drift.
Integration tests — full Run execution across a multi-step Zap in a sandboxed tenant, including Paths/Filters/Formatter logic.
Load tests — sustained and burst task throughput against the Execution Engine and queue, validating the tenant-fair scheduling guarantees.
Security tests — sandbox escape attempts against the Piece Runtime, credential-isolation verification, and periodic third-party penetration testing.
AI/Agent evaluation — prompt regression suites for Copilot and Agents, measuring task-completion accuracy and guardrail adherence before each model or prompt change ships.
23.2 Release Process
Feature branch → automated unit/contract/integration test suite → staging deploy.
Staging smoke test against a representative set of real (sandboxed) third-party accounts per major app category.
Canary rollout to a small percentage of production traffic with automated rollback on elevated error rate.
Full production rollout with monitoring dashboards watched through the deployment window.

27. Appendix — Glossary of Terms
Term
Definition
Zap
A single automated workflow: one trigger followed by one or more actions
Trigger
The event that starts a Zap
Action
An operation performed in an app when a Zap runs
Search
A lookup for existing data in a connected app
Task
One completed action step in one Zap run; the primary billing unit
Piece / Connector
An app's integration definition: its auth method plus its triggers, actions, and searches
Path
A multi-branch conditional router inside a Zap
Filter
A single-branch gatekeeper that stops a Zap unless conditions are met
Formatter
A built-in, task-free data-transformation step
Sub-Zap
A reusable Zap called by another Zap as a sub-routine
Table
Zapier's built-in automation-native database
Interface
A no-code form, page, or mini-app connected to Zaps/Tables
Canvas
An AI-assisted visual diagramming tool that can generate real Zaps/Agents/Tables/Interfaces
Chatbot
A no-code AI chatbot trained on your content and connected to automation
Agent (Central)
A goal-driven, autonomous AI teammate with a scoped tool allow-list
Copilot
The natural-language AI build-assistant embedded across every product
MCP (Model Context Protocol)
A standard exposing app actions as callable tools to external AI assistants
Run
One execution of a Zap from trigger to final step
Zap History
The per-run, per-step execution log and audit trail
Digest
A step that batches multiple trigger events into one periodic summary
Transfer
A bulk, one-time migration tool for existing historical records
SCIM
System for Cross-domain Identity Management; automated user provisioning from an identity provider
SSO/SAML
Single sign-on via a corporate identity provider
RBAC
Role-Based Access Control
OAuth 2.0
The delegated-authorization protocol most app connections use to grant access without sharing a password
Webhook
An HTTP callback that pushes an event to a URL the instant it happens, powering instant triggers
Polling
Checking an app's API on a fixed interval to detect new data, used when no webhook is available
Sandbox / Piece Runtime
The isolated execution environment that runs a connector's or Code step's logic safely per tenant
Idempotency Key
A unique identifier attached to an action call so a retried request cannot cause a duplicate side effect
Dead-Letter Queue
A holding queue for Runs that exhausted all retries, used for manual or automated follow-up
Row-Level Security
A database access-control technique that restricts each query to only the requesting tenant's rows
Envelope Encryption
Encrypting a data key with a master key, so credentials can be rotated without re-encrypting all data
SOC 2 Type II
An audit certifying an organization's security controls operated effectively over a period of time
DPA (Data Processing Agreement)
A legal contract governing how a vendor processes a customer's personal data
BAA (Business Associate Agreement)
A HIPAA-required contract between a covered healthcare entity and its vendor
Line Item
A repeating sub-field structure (e.g., order items) represented as an array within trigger data
Sample Data
The example payload pulled during a step test, used to power the field-mapping picker
Draft State
A Zap's unpublished, in-progress configuration that has not yet gone live
Published State
A Zap's live, currently running configuration
Custom/Private App
An integration built for internal use only, not submitted to the public directory
Shared App Connection
One authenticated connection reused across many users within a workspace
Guardrail (AI)
A policy constraint that bounds what an AI Action or Agent is allowed to do at runtime
