1. Executive Summary
This document is the foundation-level companion to the full production specification: instead of cataloguing every product feature, it isolates one question and answers it completely — how does a connection, an integration, and a workflow actually bind together, from the moment a user clicks "Connect" to the moment a live run executes across many apps at once. It then applies that same theory to Copilot, the AI build-assistant, and closes with the widest practical integration catalog: 400+ representative apps grouped by category, each with its typical authentication method and typical trigger/action pattern.
Read this document as the "how it actually works" layer underneath the feature catalog. Nothing here is product marketing — it is the mechanical, backend-level truth of how an App/Piece definition, a Connection record, a Workflow graph, and a Run context relate to one another at runtime, applicable to any of the integrations listed later.
2. Foundation Objects — What Actually Exists Under the Hood
Everything the product does — Zaps, Tables, Interfaces, Chatbots, Agents, Copilot — is built from the same small set of foundation objects. Understanding these four objects and how they reference each other explains the entire platform.

2.1 Why the Separation Matters
A Step never stores credentials directly — it stores a connection_id. This is what lets one Connection be reused across dozens of workflows, and lets a credential be rotated or revoked in exactly one place without touching every workflow that uses it.
A Piece never stores tenant data — it is pure code, shared by every workspace on the platform. The same Slack Piece definition executes for every customer; only the Connection it's handed at runtime differs.
A Workflow never stores live data — the graph is just structure (which step follows which, which fields map to which). The actual values only exist inside a Run, created fresh each time the workflow executes.
A Run never modifies the Workflow — so a workflow can be safely inspected, edited as a draft, or rolled back to a prior version without disturbing runs that are in flight or already completed.
2.2 The Reference Model
In relational terms: Workspace has many Connections; Workspace has many Workflows; Workflow has many Steps; each Step references exactly one Piece (by app key + version) and at most one Connection; Workflow has many Runs; each Run has many Run-Step-Results, one per Step, holding that step's actual input and output payload for that specific execution. Nothing here is unique to any single vendor's product — this is the same shape underneath Zapier, Activepieces, Make, and n8n.
3. The Complete Connection & Setup Flow (Theory)
This is the single flow every integration follows, regardless of which of the 400+ apps in the catalog it is. Only the specific fields and auth mechanics change per app — the sequence of stages never does.
3.1 Stage 1 — App Selection
The user searches or browses the App/Piece directory and picks an app.
The platform loads that Piece's manifest: its declared authentication schema, and the list of triggers, actions, and searches it exposes, each with its own input/output field schema.
Nothing is authenticated yet at this stage — this is purely reading a static, versioned definition from the Piece registry.
3.2 Stage 2 — Authentication
The platform reads the Piece's auth_schema and renders the appropriate UI: an OAuth "Connect" button, an API-key input field, a username/password form, or a custom multi-field form for non-standard auth.
For OAuth2: the platform's backend builds an authorization URL using the Piece's registered client_id and required scopes, and opens it in a popup pointed at the third-party's own login page. The user authenticates there — the platform never sees their third-party password.
For API key/Basic auth: the raw value the user types is sent directly to the backend over TLS and is never persisted in the browser, not even temporarily.
3.3 Stage 3 — Token Exchange & Storage
The third-party service redirects back to the platform's OAuth callback endpoint with a short-lived authorization code.
The platform's backend — never the browser — exchanges that code for an access token and a refresh token, using the Piece's client_secret, which is never exposed to the frontend.
The access and refresh tokens are encrypted with the tenant's data key (envelope encryption) and written as a new row in the Connections table.
The browser receives back only a connection_id — an opaque reference — never the raw token.
For API-key apps, the same encryption and storage step happens directly on the pasted value, skipping the OAuth-specific steps.
3.4 Stage 4 — Step Configuration & Dynamic Fields
The user picks a specific trigger or action event exposed by the Piece (e.g., "New Row", "Send Message").
Some input fields are static (typed text); others are dynamic dropdowns that the platform populates by calling the third-party's API live, using the just-created Connection, to list real options (e.g., "which spreadsheet", "which channel").
Fields can be marked as cascading — selecting one field's value triggers another live API call to refresh a later field's options (e.g., picking a spreadsheet reloads the list of available sheet tabs inside it).
Every input field the user fills in this stage is stored as a Field Mapping: either a literal value, or a reference expression pointing at another step's output.
3.5 Stage 5 — Test Step
The platform executes the configured step exactly once, for real, using the live Connection, and returns actual sample data — a real row, a real recent email, a real API response.
This sample becomes the schema the field-mapping picker uses for every step added afterward — this is why later steps can offer "insert data from Step 2" with real field names, not just guesses.
For action steps, the test genuinely performs the action (e.g., it really sends a test Slack message) so the mapping can be visually confirmed against real output.
3.6 Stage 6 — Publish
Publishing moves the workflow from Draft to Published state and creates a restorable version snapshot.
For instant/webhook-based triggers, publishing calls the third-party app's subscribe API (using the Connection) to register a webhook URL unique to this workflow.
For polling triggers, publishing registers a scheduled job that will call the app's list/search API on an interval, tracking a cursor (usually a timestamp or last-seen ID) to detect only new items.
Until this stage, nothing about the workflow is "live" from the third-party app's point of view — Draft edits never touch anything external.
3.7 Stage 7 — Live Execution
An external event arrives (webhook push) or a polling tick discovers new data.
The platform creates a new Run, resolves every Field Mapping against the data accumulated so far in that Run, and executes each Step in order using its bound Connection.
Every step's input and output is persisted immediately to that Run's history — this is what later powers the per-run inspection view.
4. Authentication Patterns — Every Auth Type, Flow by Flow
Every one of the 400+ apps in the catalog authenticates using one of five underlying patterns. Knowing which pattern an app uses tells you exactly what setup flow to expect before you ever open its directory page.
4.1 OAuth 2.0 (Authorization Code Flow) — the majority of apps
User clicks Connect.
Backend builds an authorization URL: {app_auth_url}?client_id=...&redirect_uri=...&scope=...&state=... and opens it in a popup.
User logs into the third-party app directly and approves the requested scopes.
Third-party redirects to the platform's callback URL with a one-time authorization code and the original state value (checked to prevent CSRF).
Backend exchanges the code for an access_token and refresh_token via a server-to-server POST, using client_secret.
Tokens are encrypted and stored as a Connection; popup closes; UI shows "Connected".
On every future use, if the access token has expired, the backend silently uses the refresh_token to get a new one before the step runs — invisible to the user unless the refresh itself fails (e.g., access was revoked), which surfaces as a reconnect prompt.
Examples: Google Workspace apps, Slack, HubSpot, Salesforce, Shopify, Microsoft 365, Zoom, Asana, Notion, Trello.
4.2 API Key
User generates a key inside the third-party app's own dashboard (outside the platform entirely).
User pastes it into a single field on the platform's Connect screen.
Backend validates it with a lightweight test call, then encrypts and stores it as a Connection — no popup, no redirect, no refresh cycle since API keys are typically long-lived until manually rotated.
Examples: Stripe (secret key), Mailchimp, SendGrid, OpenAI, Anthropic, most developer-tool and infrastructure apps.
4.3 Basic Auth (Username + Password or Username + Token)
User enters two fields directly on the platform; both are sent to the backend over TLS and encrypted at rest as a single Connection payload.
Common for older or self-hosted systems without a modern OAuth implementation, and for some project-management and ticketing tools using a username plus an API token in place of a password.
Examples: some Jira/Confluence self-hosted instances, legacy FTP/SFTP-based systems, certain on-prem CRMs.
4.4 Custom / Multi-Field Auth
The Piece defines an arbitrary set of fields (e.g., subdomain + API key + region, or client ID + client secret + account ID) instead of a standard OAuth or single-key flow.
The platform renders exactly the fields the Piece declares, validates them with a defined test call, then stores the full set as one encrypted Connection payload.
Examples: Zendesk (subdomain + token), NetSuite, some enterprise ERP/CRM systems with account-specific endpoints.
4.5 No-Auth / Webhook-Native
No Connection object is created at all — the platform simply generates a unique inbound URL, and any system capable of sending an HTTP request can trigger the workflow by posting to it.
Outbound HTTP actions similarly need no stored Connection unless the target API itself requires a key, which is then handled as API-key auth above.
Examples: Webhooks by Zapier / generic HTTP triggers, custom internal systems, IoT devices, any REST API without a dedicated Piece yet.

5. How a Workflow Run Actually Executes, Step by Step
This section walks through the runtime mechanics once a workflow is published and live — the part that happens with no user watching, potentially thousands of times a day.
5.1 Event Arrival
Instant/webhook apps — the third-party app sends an HTTP POST to the unique webhook URL generated during publish. This request typically arrives within milliseconds of the real-world event.
Polling apps — a scheduled job wakes up on its configured interval, calls the app's list/search endpoint using the stored Connection, and compares results against the last-seen cursor to isolate genuinely new items.
5.2 Run Creation
The Trigger Service normalizes the incoming payload into the workflow's expected trigger schema.
A new Run row is created: status = running, started_at = now, workflow_id + workflow_version pinned to the currently published version (so an in-flight run is never affected by a later edit).
The normalized trigger payload is stored as the Run's step_1 result, immediately queryable.
The Run is handed to the Execution Engine via the task queue.
5.3 Step-by-Step Walk
The Execution Engine loads the next Step in the graph.
If the Step is a Filter or Path condition, it evaluates the rule against the accumulated Run data and decides whether to continue, branch, or halt — no external app is called for this.
If the Step is an Action/Search, the Engine resolves every Field Mapping by reading from the Run's accumulated data (e.g., {{step_1.email}} pulls the literal value from step_1's stored output).
The Engine loads the Step's bound connection_id, decrypts the credential inside an isolated sandbox (never outside it), and invokes the Piece's perform() function for that action with the resolved inputs.
The Piece code makes the real HTTP call to the third-party API and returns a result.
The result is written to that Step's Run-Step-Result row, and becomes available to every subsequent Step in the same Run.
The Engine advances to the next Step and repeats until the graph is exhausted or a Filter halts it.
5.4 Failure Handling
Transient failure — (e.g., third-party API returned a 503) triggers an automatic retry on an exponential backoff schedule before being marked a hard failure.
Auth failure — (e.g., token was revoked, refresh failed) marks the Connection as needing reconnection and notifies the workspace owner directly, since no retry can fix it.
Hard failure — after retries are exhausted, the Run is marked failed, an error notification fires, and the Run's data remains fully inspectable for debugging.
Repeated failure — if a workflow fails on every run for a sustained period, an auto-pause safeguard can disable it to prevent a runaway error loop.
5.5 Completion
Once every step succeeds (or a Filter cleanly halts the Run), the Run's status is set to success or filtered.
The Run's total task count (one per completed Action/Search step) is reported to the Billing & Metering service.
The full Run — every step's exact input and output — remains stored and queryable for as long as the workspace's retention policy allows.
6. Copilot — From Natural Language to Published Workflow
Copilot sits on top of the exact same foundation objects described in Section 2 — it does not have its own parallel data model. What it changes is who fills in Stages 1 through 6 of the setup flow: instead of a human clicking through the app directory and each field one at a time, an LLM proposes the whole graph and the human reviews it.
6.1 The Copilot Pipeline
Prompt intake — the user describes the desired automation in plain language ("when someone fills out my Typeform, add them to HubSpot and post to Slack").
Intent parsing — the model extracts the implied trigger, the implied sequence of actions, and the apps involved from the sentence.
App resolution — each implied app name is matched against the real Piece directory (fuzzy-matched against app display names and aliases) to find the actual Piece definitions to use.
Connection resolution — for each resolved Piece, Copilot checks whether the user already has an existing Connection for that app; if not, it inserts a "Connect" prompt into the draft graph at that step instead of guessing credentials.
Trigger/action selection — Copilot picks the most likely specific event from each Piece's exposed list (e.g., "New Form Submission" rather than a less relevant event on the same app) based on the described intent.
Field mapping generation — Copilot inspects each Piece's declared input schema and each upstream step's declared output schema, and proposes mappings (e.g., mapping Typeform's email field to HubSpot's email field) using field name/type similarity plus semantic matching, not fixed rules.
Draft assembly — the proposed trigger, actions, and mappings are written into a real Draft-state Workflow record — an actual editable graph, not a preview image.
Human review — the user sees the same Zap editor UI as if they'd built it by hand, with every step pre-filled; they can edit, delete, reorder, or reconnect any step before publishing.
Test and publish — identical to the manual flow: Stage 5 (Test Step) and Stage 6 (Publish) run exactly as described in Section 3, with no special-cased AI-only publish path.
6.2 What Copilot Cannot Skip
Authentication — Copilot can never complete Stage 2/3 (auth) on the user's behalf; a human must always approve the OAuth popup or paste an API key themselves. This is a hard security boundary, not a product limitation.
Final publish confirmation — a generated draft never auto-publishes; a human explicitly reviews and turns it on, exactly as with a hand-built workflow.
Ambiguous field mappings — when Copilot's confidence in a proposed mapping is low (e.g., no clearly matching field name/type), it leaves that field blank and flags it for manual completion rather than guessing silently.
6.3 Refinement Loop
If a test run behaves unexpectedly, the user can describe the problem in plain language ("it's not filtering out test submissions") and Copilot edits the existing Draft graph directly — inserting a Filter step, adjusting a condition, or fixing a mapping — rather than starting over.
This refinement operates on the same Draft/Published state model as manual edits: nothing changes for a live Published workflow until the edited Draft is explicitly republished.
6.4 Cross-Product Generation
The same pipeline generalizes beyond single workflows: given a broader prompt, Copilot can produce a Table schema (inferring Fields and types from the described data), an Interfaces form (inferring input fields from the described intake), and the connecting Workflow(s) between them, all in one pass — because Tables, Interfaces, and Workflows share the same foundation-object model described in Section 2, just with different node types in the graph.

8. Full Worked Examples Across Categories
Each example below names the specific apps, their auth pattern, and the exact Connection/Field-Mapping mechanics from Sections 3–5 — showing the same theory applied to different category combinations.
8.1 Sales: Lead Capture to CRM to Notification
Apps: Facebook Lead Ads (OAuth 2.0) -> Salesforce (OAuth 2.0) -> Slack (OAuth 2.0).
Three separate Connections are created ahead of time: one for the ad account, one for the Salesforce org, one for the Slack workspace.
Trigger: New Lead in Facebook Lead Ads fires the moment someone submits a lead form; the payload is stored as step_1.
Action 1: Create Lead in Salesforce, with fields mapped from {{step_1.email}}, {{step_1.full_name}}, {{step_1.phone_number}}; the Engine decrypts the Salesforce Connection and calls its API, storing the new lead_id as step_2.
Action 2: Send Channel Message in Slack, with the message template referencing {{step_2.lead_id}} and {{step_1.full_name}}; the Engine decrypts the Slack Connection and posts the message.
8.2 Finance: Invoice Extraction to Accounting to Approval
Apps: Gmail (OAuth 2.0) -> AI Action (API Key) -> Table (native) -> QuickBooks (OAuth 2.0) -> Interfaces (native).
Trigger: New Email Matching Search in Gmail, filtered to a specific label, fires on any invoice email; the attachment is stored as step_1.
Action 1: an AI Action calls a model provider (using an API-key Connection) to extract structured fields from the attached PDF, stored as step_2.
Action 2: Create Record in a Table writes the extracted invoice into an AP Queue, stored as step_3.
A Path step branches on {{step_2.amount}}: under threshold proceeds directly; over threshold routes to an Interfaces approval form referencing {{step_2.vendor}} and {{step_2.amount}}.
On approval, Create Bill in QuickBooks runs using the QuickBooks Connection, mapped from step_2's extracted fields.
8.3 IT/DevOps: Incident Response Chain
Apps: PagerDuty (API Key) -> Slack (OAuth 2.0) -> Table (native) -> SMS via Twilio (API Key).
Trigger: New Incident in PagerDuty fires via webhook the instant an alert is created; stored as step_1.
Action 1: Create Channel in Slack, named using {{step_1.incident_id}}, using the Slack Connection.
Action 2: Create Record in a Table logs the incident with {{step_1.severity}} and {{step_1.service_name}}.
A Looping step iterates over the on-call list pulled from the Table, and for each person runs Send SMS via the Twilio Connection, mapped from {{loop.phone_number}} and {{step_1.incident_id}}.
8.4 E-commerce: Order to Fulfillment to Support
Apps: Shopify (OAuth 2.0) -> ShipStation (API Key) -> Zendesk (custom multi-field: subdomain + token).
Trigger: New Order in Shopify fires via webhook; the order payload is stored as step_1.
Action 1: Create Shipment in ShipStation, mapped from {{step_1.shipping_address}} and {{step_1.line_items}}, using the API-key Connection.
A Filter step checks {{step_1.tags}} for a "VIP" tag; if present, Action 2 (Create Ticket in Zendesk, flagged priority-high) runs, using the subdomain+token Connection resolved against that specific store's Zendesk instance.
8.5 Cross-Category: Database-Native Sync (No Pre-Built Piece)
Apps: PostgreSQL (custom multi-field: host/port/credentials) -> HubSpot (OAuth 2.0).
Trigger: a polling job runs on Schedule, querying a PostgreSQL table via a direct database Connection (host, port, database name, username, password, all encrypted together as one Connection payload) for rows where updated_at is newer than the last-seen cursor.
For each new/changed row, Search or Create in HubSpot looks up the contact by email; if not found, creates it, mapped from the row's columns.
This demonstrates that the same theoretical flow — Connection, Field Mapping, Run context — applies identically whether the source system is a SaaS app with a REST API or a raw database with no API at all.
9. Setup Checklist by Auth Type
A condensed, practical checklist derived directly from Section 4 — what to actually prepare before connecting an app in each auth category.
9.1 Before Connecting an OAuth 2.0 App
Confirm you're logged into the correct account/organization in that third-party app in your browser before starting the Connect flow, since the popup will use whichever session is already active.
Confirm you have admin or sufficient permission in that app to grant the requested scopes.
If the platform is self-built and this is a new integration, confirm the OAuth app has been registered in that vendor's developer console with the correct redirect URI.
9.2 Before Connecting an API-Key App
Generate the key from inside the third-party app's own dashboard, with the narrowest scope/permission level that still covers the actions you need.
Store a backup of the key somewhere secure outside the platform, since most providers only show a secret key once at creation time.
9.3 Before Connecting a Custom Multi-Field App
Gather every required field in advance (subdomain, account ID, region, environment) — these flows fail most often from an incomplete field set, not bad credentials.
Confirm whether the app distinguishes sandbox/test credentials from production credentials, and connect the correct one for your intended use.
9.4 Before Using a No-Auth/Webhook Integration
Confirm the sending system can reach the public internet (an internal-only system behind a firewall cannot POST to a public webhook URL without a tunnel or relay).
Plan for payload validation (e.g., a shared secret in the request) since no-auth endpoints have no platform-enforced verification of the sender's identity by default.
10. Appendix — Glossary of Terms
Term
Definition
App / Piece
A versioned integration definition: its auth schema plus its triggers, actions, and searches
Connection
An encrypted, reusable credential record tied to one App and one owner, referenced by ID only
Workflow / Step Graph
A directed graph of Steps, each referencing a Piece, a Connection, and its field mappings
Field Mapping
A reference expression (e.g., {{step_1.email}}) resolved against a Run's accumulated data at execution time
Run
One execution instance of a workflow, holding the real data that flowed through every step
Run-Step-Result
The stored input/output payload for one specific step within one specific Run
OAuth 2.0
An authorization flow where the platform never sees the user's third-party password, only an exchanged token
Refresh Token
A long-lived credential used to silently obtain new access tokens without re-prompting the user
Webhook
An inbound HTTP callback a third-party app sends the instant an event occurs
Polling
Checking a third-party app's API on an interval to discover new data, using a cursor to avoid duplicates
Cursor
A saved marker (timestamp or ID) used by a polling trigger to identify only new items since the last check
Sandbox
The isolated execution environment that decrypts credentials and runs a Piece's code per tenant, per invocation
Draft / Published State
A workflow's unpublished editing state vs. its live, currently-running state
Copilot
The AI build-assistant that fills in the setup flow's stages from a natural-language prompt, subject to human review
Auto-Pause
A safeguard that disables a workflow after sustained repeated failures to prevent a runaway error loop
Task
One completed action/search step within one Run — the typical billing unit
